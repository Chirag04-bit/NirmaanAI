# NirmaanAI Operational Recommendation Engine — Architecture & Subsystem Specification

**Phase:** Phase 15 — Recommendation Engine  
**Subsystem:** Decision Support Layer (`src/decision/`)  
**Governance:** Human-in-the-Loop Decision Support (`requires_operator_verification = True`)

---

## 1. Subsystem Objective & Core Philosophy

The NirmaanAI Recommendation Engine transforms multi-phase analytical signals (from Phases 6 through 14) into prioritized, deterministic, and evidence-grounded operational guidance for manufacturing MSMEs.

The subsystem operates under strict scientific and industrial principles:
1. **Decision Support, Not Autonomous Control:** The system never executes machine shutdowns or inventory orders autonomously. Every recommendation requires human operator/supervisor authorization.
2. **Deterministic & Auditable Reasoning:** Every recommendation is generated by auditable rules with explicit antecedents and locked operational thresholds. No black-box LLM hallucinations or opaque heuristic weightings are used to generate core actions.
3. **Multi-Domain Corroboration:** Priority and evidence strength depend strictly on cross-subsystem corroboration across 5 physical/operational domains:
   - `TELEMETRY_ANOMALY` (Phase 7)
   - `PREDICTIVE_FAILURE` (Phase 6)
   - `PRODUCTION_FLOW` (Phase 8)
   - `DIAGNOSTIC_RCA` (Phase 12)
   - `INVENTORY_SPARE` (Phase 10)
4. **Diagnostic & Financial Isolation:** Financial loss (Phase 14) provides economic context but is **never** treated as an independent physical evidence domain. Furthermore, zero pseudo-financial equations are computed ($₹ \ne f(\text{Health})$, $₹ \ne f(\text{SHAP})$, $₹ \ne f(\text{RCA})$).

## 2. Architecture & Component Structure

```
src/decision/
├── __init__.py                     # Exposes Loss and Recommendation APIs
├── loss_models.py                  # Phase 14 Financial loss models
├── loss_engine.py                  # Phase 14 Mathematical equations
├── loss_service.py                 # Phase 14 Factory loss orchestration
├── recommendation_models.py        # Pydantic v2 schemas, closed taxonomy, evidence items
├── recommendation_rules.py         # Deterministic domain rules with locked thresholds
├── recommendation_engine.py        # Deduplication, conflict resolution, ranking
└── recommendation_service.py       # Upstream ingestion, temporal filtering, reporting
```

### 2.1 Core Modules
- **`recommendation_models.py`**:
  - `RecommendationCategory`: 5 controlled categories (`MAINTENANCE`, `PRODUCTION_FLOW`, `INVENTORY`, `ENERGY`, `MONITORING`).
  - `RecommendationAction`: Closed taxonomy of **strictly 26 approved actions** across the 5 categories.
  - `RecommendationPriority`: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `MONITOR`.
  - `ActionUrgency`: `IMMEDIATE`, `SAME_DAY`, `NEXT_SHIFT`, `SCHEDULED_MAINT`, `ROUTINE`.
  - `EvidenceStrength`: `STRONG` ($\ge 3$ physical domains), `MODERATE` (2 domains), `WEAK` (1 domain), `INSUFFICIENT` (sub-threshold/nominal).
  - `EvidenceItem`: Atomic record preserving its individual epistemic provenance.
  - `InventoryEvidenceContext`: Explicitly separates `observed_current_stock` (2.0) from `projected_post_action_stock` (1.0).
  - `FinancialEvidenceContext`: Quotes Phase 14 figures verbatim without pseudo-financial math.
- **`recommendation_rules.py`**:
  - Encapsulates domain logic (`R-M01` to `R-O01`) with locked thresholds ($P(\text{fail}) \ge 0.91$, Anomaly $\ge 0.2405$, Cycle Ratio $\ge 1.20$, Health bands).
- **`recommendation_engine.py`**:
  - Deduplication: consolidates redundant alerts on the same machine/component, merging evidence and unioning source phases.
  - Conflict Resolution: enforces physical safety over throughput, inventory protection over cash conservation, and bottleneck throughput over off-peak energy pause.
  - Sorting: deterministic ranking by Priority $\to$ Urgency $\to$ Machine ID $\to$ Recommendation ID.
- **`recommendation_service.py`**:
  - Orchestrates evaluation at any `as_of_timestamp` enforcing strict temporal causality ($t_{\text{evidence}} \le t_{\text{decision}}$).

## 3. Epistemic Provenance Integrity

Every output strictly preserves epistemic classification:
- `OBSERVED`: Raw sensor telemetry, observed on-hand inventory stock, actual scrap units.
- `DERIVED_FROM_OBSERVED`: Model predictions (Phase 6 failure prob), reconstruction error (Phase 7), bottleneck classification (Phase 8), RCA candidate (Phase 12), Health score (Phase 13), realized loss (Phase 14).
- `CONFIGURED_ASSUMPTION`: Warning band boundaries ($0.75 \le P < 0.91$), safety stock and ROP formulas, supplier lead time catalog, energy peak tariffs, financial materiality threshold (₹25,000).
- `PROJECTED`: Projected post-action inventory stock ($2.0 - 1.0 = 1.0$).
- `PROJECTED_OPPORTUNITY_COST`: Unearned contribution margin from delayed bottleneck throughput.
- `CONTROLLED_SYNTHETIC`: Scenario validation wrapper for simulated degradation chains.
